Check-expiry and Slack notification workflow
============================================

Purpose
-------
A reusable GitHub Actions workflow that reports the Snyk vulnerabilities tracked
in an environment and how close each is to becoming non-compliant. It sends a
Slack message to the cyber-dojo-alerts channel and writes a GitHub step summary.
It makes NO Kosli calls and has no effect on compliance status.

It is called once per environment by aws-beta.yml and aws-prod.yml, after that
environment's scan has run. The data it reports on is produced earlier in the
same GitHub Actions run by artifact_snyk_test.yml, which uploads one
<repo>-vuln-reports.json file per artifact.


Two expiry mechanisms
---------------------
Each <repo>-vuln-reports.json file holds one artifact's policy input and the
vuln_reports rule from the same kosli evaluate input (--output-rule
vuln_reports) that decides the artifact's snyk decision attestation:

  {
    "vulns":        [ the per-vuln matrix data, with first_seen_ts and now_ts ],
    "vuln_reports": { full_id: { mechanism, days_remaining, ... } }
  }

The deadline arithmetic lives only in the rego (snyk-vuln-compliance.rego),
which uses max_days_by_severity from rego.params.{env}.json:

  aws-beta:  critical=1, high=2, medium=4,  low=10
  aws-prod:  critical=1, high=5, medium=10, low=30

Each vuln gets a vuln_reports entry under one of three mechanisms:

  dot_snyk_expiry -- the vuln has a .snyk ignore entry with an expiry date.
    days_remaining = (ignore_expires_ts - now_ts) / 86400

  dot_snyk_forever -- the .snyk ignore entry has no expiry date: compliant
    regardless of age, no deadline, and not reported.

  rego_limit -- the vuln has no .snyk ignore entry, so the rego age limit applies.
    age_days = (now_ts - first_seen_ts) / 86400
    days_remaining = max_days_by_severity[severity] - age_days

first_seen_ts ahead of now_ts means no age can be measured, and the rego gives
that vuln no vuln_reports entry. Both timestamps come from one read of one trail
(created_at and last_modified_at), so that ordering would mean the server
reported a last_modified_at earlier than the created_at of the same object.
stamp_vuln_times.py fails the scan on it, and the report exits 45 on any vuln
with no entry rather than quote a deadline nobody computed.

days_remaining is positive while the vuln is still compliant and zero or negative
once it is already non-compliant. Both compliant and already-non-compliant vulns
are reported (the report is informational; the nightly scan owns the verdict).


.github/workflows/check-expiry-and-notify.yml
----------------------------------------------
Trigger: workflow_call
  inputs:  kosli_env (required)
  secrets: SLACK_WEBHOOK_URL (required)

env block:
  GITHUB_RUN_URL     link to this Actions run
  RESPONSE_GUIDE_URL link to docs/expiry-response.md

Single job: check-expiry (runs-on: ubuntu-latest)
  1. actions/checkout@v6
  2. actions/download-artifact@v8 -- pattern *-vuln-reports.json, merge-multiple, into vulns/
  3. Find vulns:
       ./bin/find_expiring_vulns.py --env <kosli_env> --vuln-dir vulns
       Then, into GITHUB_ENV:
         VULNS_JSON    the .vulns array
         STATUS_SYMBOL ./bin/print_slack_status_symbol.py --vulns "$VULNS_JSON"
         SLACK_MESSAGE ./bin/print_slack_vuln_message.py --vulns "$VULNS_JSON"
  4. Send Slack:
       "Environment: <kosli_env> <STATUS_SYMBOL>\n<SLACK_MESSAGE>\n
        See: <GITHUB_RUN_URL>\nResponse guide: <RESPONSE_GUIDE_URL>"
  5. Send Slack -- workflow failure (if: failure())
  6. Write GitHub step summary:
       ./bin/print_expiring_vulns_summary.py --env <kosli_env> --vulns "$VULNS_JSON"
       >> $GITHUB_STEP_SUMMARY


.github/actions/send-slack-message/action.yml
----------------------------------------------
Composite action. Kept local so snyk-scanning has no cross-repo action dependency.

  inputs:
    message:   required
    slack_url: required

  Posts a single Slack "section" block (mrkdwn) containing the message via
  curl -X POST --fail to slack_url.


bin/find_expiring_vulns.py
--------------------------
CLI:
  ./bin/find_expiring_vulns.py --env <env> --vuln-dir <dir>

Globs *-vuln-reports.json in <dir> and joins each vuln to its vuln_reports
entry by full_id, leaving out dot_snyk_forever vulns. It does no deadline
arithmetic of its own. Writes a JSON object to stdout and exits 0, or exits 45
naming a vuln with no vuln_reports entry:

  {
    "vulns": [
      {
        "env":            "aws-beta",
        "trail_name":     "runner-high-SNYK-GOLANG-...",
        "full_id":        "SNYK-GOLANG-...",
        "severity":       "high",
        "vuln_url":       "https://security.snyk.io/vuln/...",
        "mechanism":      "dot_snyk_expiry" | "rego_limit",
        "days_remaining": 19.8,
        "ignore_expires": "2026-06-01 10:53:10+00:00" | null,
        "age_days":       5.16 | null,
        "limit_days":     10 | null,
        "artifact":       "runner"
      }
    ]
  }

The list is sorted by whole-day deadline, then severity, then trail_name, so the
soonest-to-expire (or most-overdue) vuln is first. Ties are broken by severity
rather than by the raw fractional day count, because vulns sharing one .snyk
ignore entry differ by a few seconds of jitter that would otherwise decide the
order. "artifact" is the trail_name segment before the first -severity- part.
Every number in a row comes from the evaluation that decided the attestation,
so the report and the decision cannot disagree.


bin/print_expiring_vulns_summary.py
-----------------------------------
CLI:
  ./bin/print_expiring_vulns_summary.py --env <env> --vulns '<json array>'

The --vulns value is the .vulns array from find_expiring_vulns.py. Writes
Markdown to stdout for the GitHub step summary:

  ## <env> (Snyk vulns tracked: Count=N)

  then one table per severity, in order critical, high, medium, low:

  ### <Severity> (Count=N)

  | Artifact | Days remaining | Mechanism | Vuln ID |

  (or "No vulnerabilities." when that severity has none). Rows are sorted by
  days_remaining ascending. Mechanism is displayed as "rego" (rego_limit) or
  ".snyk" (dot_snyk_expiry). Vuln ID is a Markdown link [full_id](vuln_url).

Example output:

  ## aws-beta (Snyk vulns tracked: Count=2)

  ### Critical (Count=0)

  No vulnerabilities.

  ### High (Count=1)

  | Artifact | Days remaining | Mechanism | Vuln ID |
  |----------|----------------|-----------|---------|
  | runner | 20 | .snyk | [SNYK-GOLANG-GOLANGORGXNETHTTP2-16535157](https://security.snyk.io/vuln/SNYK-GOLANG-GOLANGORGXNETHTTP2-16535157) |

  ### Medium (Count=0)

  No vulnerabilities.

  ### Low (Count=1)

  | Artifact | Days remaining | Mechanism | Vuln ID |
  |----------|----------------|-----------|---------|
  | creator | 5 | rego | [SNYK-ALPINE322-NGHTTP2-16426989](https://security.snyk.io/vuln/SNYK-ALPINE322-NGHTTP2-16426989) |


bin/print_slack_status_symbol.py
--------------------------------
CLI:
  ./bin/print_slack_status_symbol.py --vulns '<json array>'

Prints :x: when the list is non-empty and its first vuln has days_remaining <= 0,
otherwise :white_check_mark:. days_remaining is tested unrounded, and zero counts
as reached, because zero is the limit day itself, which the rego denies.


bin/print_slack_vuln_message.py
-------------------------------
CLI:
  ./bin/print_slack_vuln_message.py --vulns '<json array>'

Prints "No Snyk vulnerabilities :-)" when the list is empty, otherwise the first
vuln's days line, full_id, severity, repo (artifact) and mechanism. The days line
rounds up, so 2.3 days of grace reads as 3.


What this workflow does NOT do
------------------------------
- It does not run Snyk scans.
- It does not create or modify any Kosli trails, attestations, or flows.
- It makes no Kosli calls at all; it reads the run's local *-vuln-reports.json files.
- It does not affect the compliance status of any artifact or environment.


docs/expiry-response.md
-----------------------
Linked from the Slack message. Tells the reader what to do when a vuln is
approaching (or past) its expiry, depending on which mechanism applies.
